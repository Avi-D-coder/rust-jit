# M009 procedural context representation repair

The actual matched-server fixture in m009-root-context-witness.log exposed a representation bug. Two owned root ContextRecords have different defining units and different stable keys, while the pinned hygiene store maps both to the same upstream root SyntaxContext. A macro moves the first token to the second source with located_at and gives the second token the first context with resolved_at. The former export path selected the destination anchor's context and lost the original owned root identity.

Procedural import now allocates one private RPC context label per owned context. It uses the existing pinned safe mark allocator and private hygiene database; no raw SyntaxContext construction, alternate hygiene algorithm, HIR query framework or native backend is introduced. The label is an opaque private transport mark over the registered upstream context. It provides a distinct valid wire identity when the server copies location and context separately.

Labels are not adopted into owned ContextRecords and never participate in owned name normalization or resolution. Procedural export maps the copied label back to the original owned context, independently of its source anchor. Declarative import continues using its original upstream contexts. The token schema and owned semantic keys remain unchanged. The procedural engine generation advances to 4 so older transport results cannot fulfil current demands.

The external-server regression verifies the resulting token locations belong to the second source while both selected contexts retain the first owned identity. The roundtrip regression verifies distinct private labels, unchanged owned context rows, unchanged pinned root equivalence, and exact token/context/span roundtrips. Existing native span, macro-form, grammar and hygiene fixtures remain required in Gate01. This repairs implementation evidence; it does not relax any required generated-source, trait, guest execution or release acceptance.
