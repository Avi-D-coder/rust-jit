# M013 generated derive helper scope and precedence

Revision 4 Sections 18.2, 49–51 and Section 57 milestone C, macOS ARM64,
Rust 1.99.0. M013 remains in progress. This step classifies exact declaration
metadata without granting derive execution, producer completeness or publication.

GeneratedDeriveResolution constructs the current annotation plan and export
choices, replays their positive identities, and validates every receipt against
its exact request. Missing declarations or unresolved exports remain typed input
demands. An unavailable list never becomes ready empty metadata.

Each declared helper is indexed by its canonical name and the pinned item-name
context of the derive path's final segment. Attribute paths retain their original
span/context records. Only a bare path with that normalized context can borrow
helper visibility. Helpers apply after their introducing derive on the owning ADT,
and to its enabled fields and variants. Qualified paths, sibling ADTs, inactive
members and mismatched receipts cannot borrow that scope. Several derives may
supply one helper; their distinct occurrence identities retain lexical order.

Helpers before their introducing derive are recorded separately and remain
unresolved. Rustc's deprecated compatibility rules and ambiguity diagnostics are
still pending; this step does not silently classify those candidates as inert.
Nested item/type-expression inheritance and generated helper import restrictions
also need their full upstream cases. The normal scope and ordering above follow
[the Rust Reference](https://doc.rust-lang.org/reference/procedural-macros.html#derive-macro-helper-attributes)
and the pinned checkout's rustc_resolve helper collection.

The pinned adapter now extracts exact field/variant meta paths from the same
syntax map used for outer attributes. Argument extraction remains bound to the
selected outer item annotation. No alternate parser or reconstructed hygiene is
introduced. Materializing input delegates to the existing bound plan, preserves
helper tokens, and refuses a changed output/header/cfg/epoch. It is pure data,
not an execution certificate.

The generated catalog retains immutable decisions with stable explicit encoding
and checked metadata accounting. Repeated classification must replay the same
fingerprint within an epoch. The catalog exposes only checked counts to discovery;
after classification the producer still waits on its first derive occurrence.

The unchanged rustc derive-helper-configured case exercises cfg_attr helpers on
both the item and its field, including token preservation and changed-cfg refusal.
The newly copied derive-helper-shadowing-2 case exercises a field helper with the
same name as its derive. The controlled regression checks missing and wrong
receipts, lexical limits, qualified paths and sibling isolation. The actual
matched-server chain observes one inert generated helper after adopting two exact
declarations, two attribute invocations, and no derive invocation/seal/publication.
These are component checks, not full compiletest or LRR fixture passes.

Eight unchanged licensed cases now retain helpers, directives, snapshots, commit
and file hashes, both rustc license texts and COPYRIGHT. Fifteen component
assertions cover seven cases; all eight full native/compiletest/LRR acceptances
remain pending. expand-to-derive remains unexercised. Earlier MBE spacing and
invisible-group limits remain recorded.
