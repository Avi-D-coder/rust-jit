# E-R5-012 — `core::mem` layout intrinsics and the one layout module

October 17, 2026. Implementation record (not a spec contradiction) for `mem::size_of`, `align_of`, `size_of_val`, `align_of_val`, `needs_drop`, `discriminant`, `variant_count` `zeroed` and `transmute` under the simple-interpreter scope (E-R5-006: looser than rustc, no resource accounting; E-R5-005: one pipeline). Builds on E-R5-008 (pointers), whose synthetic `size_of` was a best-effort estimate for pointer strides only.

## Invariant

A type has exactly one size, alignment, niche and drop-glue answer. `runtime/layout.rs` is the only layout algorithm; the `core::mem` intrinsics and the synthetic pointer addresses (`runtime/cell_pointers.rs`) both consume it. Layouts follow rustc's `LayoutCalculator` (`rustc_abi::layout`) on a 64-bit target, for what the managed runtime can express. Nothing keys on a macro or an assertion; the same call lowered handwritten, from a user macro, through a generic wrapper, in a `const`/`static` initializer or as an `assert_eq!` operand reaches the same intrinsic.

## Minimal witnesses (unchanged upstream, `fixtures/upstream/rustc-checkout/tests/ui`)

`enum/enum-discrim-manual-sizing.rs` (`#[repr(u8)]`/`i64` enums, `Option<T>` under a repr), `drop/no-drop-flag-size.rs`, `consts/const-needs_drop.rs`, `functions-closures/nullable-pointer-opt-closures.rs` (`Option<closure>` niches through `&T`, `Box`, `String`), `traits/method-on-deeply-nested-struct-perf.rs`, `consts/const_discriminant.rs`, `enum-discriminant/discriminant_value-wrapper.rs`, `codegen/shift-right-operand-mutation.rs`, `numbers-arithmetic/integer-literal-suffix-inference-3.rs`. Expected numbers in `cli/mem_layout_tests.rs` are real `rustc +1.99.0 -O` output.

## Shared entry points

- **Intrinsics.** `core::mem::size_of<T>()` etc. are ordinary generic facade functions (`facade/core/mem.rs`); their bodies call closed intrinsics `core::intrinsics::lrr_size_of()`, `lrr_align_of()`, `lrr_needs_drop()`, `lrr_variant_count()`, `lrr_size_of_val(&T)`, `lrr_align_of_val(&T)`, `lrr_discriminant_value(&T)`. They are `LibraryFunction` entries (`facade/functions.rs`, tags 120-126) selected like every facade intrinsic by `select_facade_call` and executed in `engine/run_facade.rs`.
- **How the type reaches an intrinsic.** A type-argument intrinsic names no type. `LibraryFunction::type_arguments()` says how many of the *calling frame's* leading type parameters it reads; `Frame::enclosing_type_arguments` (`vm/frame_type_arguments.rs`) resolves them through the wrapper's `GenericEnv::runtime_binding(ParamKey { definition, ordinal })`. This is general: a later intrinsic (`type_name`, `zeroed`, `transmute`) declares its type-parameter count in one match arm. A value intrinsic (`size_of_val`, `discriminant`) reads the referent type of its reference argument.
- **Layout algorithm.** `runtime/layout.rs` (pure, unit-tested): scalars with niches, thin/fat pointers, `univariant` (rustc's field sort by alignment group with niche bias, `repr(C)`, `packed(N)`, `align(N)`, enum-variant prefixes), `union_layout`, `enum_layout` (single-variant-as-struct, tagged with tag widening, niche-filling with variant packing around the niche, tagged-versus-niche selection, `repr(u8/i32/C)`).
- **Declaration facts.** `runtime/cell_layout.rs` (`GuestStore::layout_demand`, `layout_of`, `needs_drop_type`, `referent_layout`, `referent_discriminant`) feeds the algorithm from type descriptors. A nominal type's declared field types, `repr` and discriminants are demanded once per declaration (`engine/run_layout.rs`, called from the `CallSeal` arm before the intrinsic's arguments seal) through `SchemaNames::bind_variant_current`, the binder constructors use, and installed in the store; field types are instantiated with a descriptor's type arguments the first time it is demanded. The intrinsic itself never reads source and never queries the database.
- **Library types.** The facade mirrors std's behavior, not always its fields (`Vec<T>;` has none, `Box<T>(T)`). `facade/library_layouts.rs` states std's real layout for the few types where they differ (`Vec`, `Box`, `Rc`/`Arc`/`Weak`, `NonNull`, `HashMap`/`HashSet`, `BTreeMap`/`BTreeSet`, `VecDeque`, `BinaryHeap`, `LinkedList`; `UnsafeCell` hides its niche, `NonZero` has one, `ManuallyDrop` never drops), keyed by crate and path like the lang items in `facade/mod.rs`. `Option`, `Result`, `Cell`, `RefCell`, `String`, ranges and every user type come from their own declarations through the same algorithm.
- **Discriminants.** `Discriminant<T>` is an ordinary facade struct holding the discriminant value (`isize`) with `Copy`, `Clone`, `PartialEq`, `Eq`, `Hash` and `Debug` in Rust. The value is the variant's declared discriminant from the descriptor's table, else its index.
- **Qualified calls with explicit type arguments** (`mem::size_of::<Foo>()`, `std::mem::size_of::<Option<Box<i32>>>()`). Three shared-pipeline gaps stood between these calls and the intrinsics, each fixed in the shared route rather than around it. (1) `ParsedFile::written_path` refused any generic argument on a call's path, so a Value goal for `mem::size_of::<u32>` stayed pending and the static numeric service could not type `assert_eq!(4, mem::size_of::<u32>())`; the callee's *final* segment arguments now belong to the call (`written_callee_spelling`, used by `qualified()` in `source_value_goals.rs` when the path is a `CallExpr` callee), as they already do for a single-name callee. (2) The dispatcher's text adapter for qualified callees (`prepare_selected_argument_call_with` in `engine/run.rs`) accepted only primitives and caller parameters; it now selects a nominal or compound argument with `resolve_written_type` + `closed_written_type`, the services typed `let` annotations use, and interns it (the adapter is now `&mut self` for that). (3) `ExplicitType::materialize` interns a written structure such as `&[u8]` or `Option<fn()>` even though the same structure is not "exact" at a coercion site.
- **`zeroed` and `transmute`.** `lrr_zeroed` / `lrr_transmute` read their type parameters like `size_of` (`type_arguments()` 1 and 2). Plain data - scalars, thin raw pointers, arrays and tuples of them - has a byte image under the layout module (`cell_layout.rs`, "Plain data"): `zeroed` builds the all-zero image, `transmute` is image to image between equal sizes (`u32`<->`f32`, `i32`<->`u32`, `usize`<->`*const T`, `[u8; 4]`<->`u32`); a thin reference is accepted as a source (its image is its address). Anything else - references as destinations, `Box`, nominal types, closures - is `LRR-E-UNSUPPORTED` naming the pair (`mem::transmute::<A, B>`), a size mismatch is `LRR-E-OP-TYPE`.

## Alternate routes removed or not added

No second layout algorithm: `type_layout`/`cell_layout`/`child_offsets` in `runtime/cell_pointers.rs` call the module (`layout_of` once a declaration's facts are known, `layout::univariant` placement for live aggregates otherwise); the old declaration-order `struct_layout` is gone. No macro- or assertion-specific path: `assert_eq!(size_of::<T>(), n)` is an ordinary call operand. No source parsing in the intrinsic. No hard-coded fixture sizes.

## Eight failure modes (AGENTS.md)

1. No separate assertion/expression evaluator: the wrappers are source functions, the intrinsics are table entries. 2. No literal-only generated-expression route. 3. No context-specific method selection or numeric inference by macro identity; `size_of::<T>()` is selected through the value namespace everywhere. 4. Generated source is not refused for supported syntax. 5. No pattern machinery. 6. Declaration facts are demanded once per declaration (`LayoutTable::declarations`) and field instantiation once per descriptor; a repeated `size_of` does no source work. 7. No namespace scan: the library table compares one crate digest and a path. 8. No body copies: facts hold `Arc<DeclarationFacts>`.

## What remains approximate or unsupported (recorded, not hidden)

- `transmute`/`zeroed` outside the byte-image model (see above); `Option<fn()>`/`Option<&T>` transmutes, reference destinations and unsized sources are refused.
- Unions: the algorithm lays them out (`union_layout`, unit-tested with `union-packed.rs`'s numbers), but the runtime has no union values or types (`constructor requires further source member/type binding`), so no program reaches it yet.
- Enum discriminants that are not integer literals need the pure constant evaluator (`literal_discriminants`); such an enum's layout is an `LRR-E-UNSUPPORTED` naming it.
- Array lengths that are expressions (`[u8; 1 << 32]`) and lengths above `u32::MAX` are outside the descriptor (`TypeKey::Array::len` is `u32`); `[u8; size_of::<u32>()]` array lengths use the pure evaluator and stay unsupported.
- Niche offsets use the same sort and bias rule as rustc, but only the count of unused patterns and the offset are modeled, not the valid range; variants that need more than one niche value use the largest niche only. Field offsets are model-only (never observable).
- Library types not in the table and not declared like std (e.g. facade-only helper structs) are laid out from the facade's fields. `Duration`, `Instant` and other std types absent from the facade are not modeled.
- Pointer arithmetic strides use the exact layout only for types whose declaration was demanded (by a prior `size_of`); other nominal types fall back to a live-structure estimate with the same `univariant` ordering (no niche, no `repr`), which agrees for plain structs and tuples.
- Coroutines, `repr(simd)`, `repr(transparent)` niche subtleties, `#[rustc_layout_scalar_valid_range_*]` on user types, `size_of_val_raw`, `align_of_val_raw`, and `dyn Trait` unsized-tail structs are not modeled.
