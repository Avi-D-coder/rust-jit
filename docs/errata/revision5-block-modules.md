# E-R5-015 — Modules written in function bodies, module-file macro admission, `crate::`/`super::` callee paths

October 21, 2026. Implementation record (not a spec contradiction) under the simple-interpreter scope (E-R5-006 looser than rustc, no resource accounting; E-R5-005 one pipeline; E-R5-009 block-local items). Architecture record written before the change and completed with the evidence below.

## Violated invariants and minimal witnesses

1. A module is a module wherever it is written. `fn main() { mod m { pub fn f() -> i32 { 1 } pub enum E { A } } assert_eq!(m::f(), 1); match m::E::A { m::E::A => {} } }` stopped at `lexical item callee requires body namespace integration` (`modules/mod-inside-fn.rs`); nested modules, `use`, `pub(super)`, impls, `crate::` and `super::` inside such a module had no route at all.
2. A function body behaves the same in every module file. `mod foo;` with `pub fn f() { assert_eq!(1, 1); println!("hi"); }` in `foo.rs` stopped at `LRR-E-CATALOG-INCOMPLETE: reached user macro requires source expansion integration` (the same function inline in `main.rs` ran).
3. `crate::` and `super::` start ordinary callee paths. `fn f() -> i32 { 3 } fn main() { let x = crate::f(); }` and `mod b { pub fn g() -> i32 { super::f() } }` stopped at `invalid macro identifier or edition: "r#crate"` / `"r#super"` / `empty or oversized macro path`.
4. rustc makes an `impl` written in any function global once its type is nameable (`privacy/required-pub-in-blocks.rs`: `S.s()` with `impl crate::S { pub fn s(&self) {} }` written in `mod m { fn f() }`, which never runs).

## Shared entry points extended (no second route)

- **A block module is a module of the enclosing module.** `syntax/outline.rs::module_segment` names an inline module that is an item statement of a block `__lrr_block_<ordinal>_<name>` (the ordinal among the file's inline block modules in source order; a byte offset would shift when a body macro's expansion is attached and the assembled tree's declarations are paired with the original outline's by identity). `block_modules` finds them in an executable body (outermost first, stopping at nested modules and token trees). The outline walker (`outline_in_root`) pushes them as ordinary module items of the module that holds the body, so their items, impls, traits, nested modules, imports and out-of-line files follow the one module route; `super` skips the anonymous block exactly as rustc's `resolve_self` does (block-local items are not visible through `super`). The same segment is used by every ancestor-derived module path: `declaration_scan.rs::lexical_context` and `ScannedModule`, `macro_calls.rs` (`module_suffix`, two sites), `modules.rs` (`external_module_declarations_from_tree`, `inline_module_layout`: a block module's out-of-line `mod x;` with `#[path]` loads like any inline module's). `lexical_context` also stops function ownership at a module boundary and `macro_calls.rs` stops the `executable` flag there: the function enclosing a module owns nothing written inside it.
- **The block's own name is a lexical alias.** `syntax/entered_macros.rs` binds the written name as a body import row `use self::<segment> as <name>` (no body-item row, so no second binder), and `outline::bind_block_module_roots` rewrites the first segment of a block-level `use` (Rust 2018+, the nearest Type-namespace binder, searched no further than the nearest module) from `m` to `self::<segment>`. Paths rooted at the alias take the existing lexical-import route: `enclosing_import_may_bind` (`syntax/thunks.rs`) and `lexical_item_may_bind` (`syntax/value_paths.rs`, Module arm removed) classify it; `ParsedFile::block_module_root` makes a two-segment `module::item` path continue from the alias exactly like the existing three-segment `root::a::b` (`source_value_goals.rs::deep_lexical`, `engine/run_nominal.rs::lexical_callee_context`), so constants, statics, tuple constructors, functions and variants of the module are selected as if written with the module's full path. The refusal `lexical item callee requires body namespace integration` is removed for modules (`syntax/thunks.rs`).
- **Std and user macros in non-root module files.** `cli/retained_entry.rs::prepare` admitted only the root file's macro-bearing bodies, so a function of a `mod x;` file reached the runtime with its macro node unattached (`engine/runtime_macros.rs::pending_source_expansion`). `admit_sibling_module_bodies` admits the macro-bearing bodies of every other original source of the entry's crate through the same `admit_retained_body`.
- **`crate::`/`super::` roots.** A path-keyword leading name is never a Type declaration: `frontend/qualified_type_names.rs` returns `NameLookup::Absent` for a keyword-only path and skips `owned_name` on a keyword; `frontend/macro_names.rs::source_segments_path` returns no path (not an error) for a route with no item name; `frontend/source_locals.rs` returns `ModuleTail` for `crate`/`super` and `frontend/local_containers.rs` skips the module-name observation for them (so `impl crate::S { .. }` written in a body resolves).
- **Impls and traits written in bodies that never run.** `cli/retained_entry.rs::prepare_container_bearing_bodies` prepares (the existing `prepare_source_local_plan`, which already publishes the member-index layer of E-R5-009) every body of the entry's crate whose blocks hold an `impl`/`trait`, found from the declaration scan's lexical scopes (innermost scope Block/Closure). Only those bodies are prepared; no other cold body is touched.
- `expand/source_declarative/assembly_anchors.rs` ignores hoisted block modules that only an expansion wrote (they have no original declaration to anchor).

## Removed / superseded

The Module arm of the lexical-item refusal; the Module body-item row for inline block modules (replaced by the import row); root-only macro-bearing body admission.

## Cost

Cold, once per file outline: one preorder walk of each executable body (skipping token trees and module subtrees) to find block modules, plus an `O(file)` ordinal count per block module and per ancestor-derived module path inside one (files without a block module pay an `O(1)` parent-kind test per module). Entry: one admission per macro-bearing body of the crate's other sources (they run only when reached) and one preparation per body holding a block-level impl/trait. Per call: unchanged.

## Acceptance scope and known gaps

Tests: `cli/module_scope_tests.rs` (all four editions, rustc outputs): macros in out-of-line, `mod.rs`, `#[path]` and nested module files; `#[macro_use]` across files; `crate::`/`super::`/`self::` callee paths; block modules with functions, enums, structs, tuple structs, constants, nested modules, `pub(crate)`/`pub(super)`, impls, traits, `use`, derives; same-named block modules in different bodies, methods, trait defaults and closures; block modules in module files; an impl written in a function that never runs. Upstream: `modules/mod-inside-fn.rs` passes in every edition.

1. A block module emitted by a macro (a statement macro expanding to `mod m { .. }`) is not hoisted: the pre-expansion outline cannot see it.
2. A local `fn` declared next to a block module that names its types (`fn p(s: m::S)`) stays `NeedOwnerContext` (E-R5-009 gap 3: header shapes capture single names only); `impl m::Tr for L` written in the same block stays `NeedImport`; `<m::S as m::Tr>::t` stays `qualified callee anchor requires further type integration`.
3. `Self::Assoc` in the signature of a member of a block-level impl (`privacy/required-pub-in-blocks.rs` reaches this after the cold-impl repair: `invalid macro identifier or edition: "Self"`).
4. `modules/mod_dir_path.rs`: the block-module half (`#[path] mod foo { mod two_macros_2; }`) loads; the macro-generated `mod two_macros_2;` (module-level or in a body) stops at `macro prelude source missing`, a pre-existing gap independent of this record; the imported fixture also lacks `modules/auxiliary/two_macros_2.rs`.
5. A `macro_rules!` written in the body before the block module is visible inside it (`fn main() { macro_rules! lm { () => { 5 } } mod m { pub fn f() -> i32 { lm!() } } .. }` runs); macro textual scoping across the hoisted module's boundary is otherwise only as exact as the outline's `OpenScope` event at the module's source position.
