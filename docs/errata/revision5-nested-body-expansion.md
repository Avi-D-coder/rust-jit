# E-R5-010 — Macro calls and Type occurrences inside block-local function bodies

October 17, 2026. Implementation record (not a spec contradiction) under the simple-interpreter scope (E-R5-006 looser than rustc, no resource accounting; E-R5-005 one pipeline; E-R5-009 block-local items). Architecture record written before the change and completed with the evidence below.

## Violated invariant and minimal witnesses

Invariant: a function declared inside a body behaves like the same function at module level once its owning body is entered. Its macro calls expand through the common hygienic engine, attach to the owning retained tree and lower through ordinary parsing, indexing, resolution and call lowering; its Type paths resolve like the same paths in a module-level body; a call between block-local functions lowers exactly like a call in the declaring body. Witnesses (rustc 1.99.0, all editions). Before the change the first three stopped with `LRR-E-EXPANSION-INPUT: local function still has pending expansion calls`, the fourth with `LRR-E-CALL-CONTEXT: entered call lowering source/body/site differs`, the fifth and sixth with `Type requires actual source authority: Source(RetainedExpansionOccurrence)` and `constructor requires further source member/type binding`:

1. `fn main() { fn f() { println!("x"); } f(); }`
2. `fn main() { fn f(a: i32) { assert_eq!(a, 3); } f(3); println!("ok"); }`
3. `fn main() { fn f(a: i32) -> String { format!("<{}>", a) } println!("{}", f(2)); }`
4. `fn main() { fn b() -> i32 { 1 } fn a() -> i32 { b() + 1 } println!("{}", a()); }` (also self- and mutual recursion of block-local functions).
5. `fn main() { fn f() -> i32 { let x: i32 = 5; x + 2u8 as i32 } println!("{}", f()); }` (annotation, cast, turbofish, record constructor of a module type inside a nested body whose enclosing body has macro expansions).
6. `fn main() { struct P { x: i32 } fn mk(x: i32) -> P { let p: P = P { x }; p } println!("{}", mk(3).x); }` (a nested body names a type its declaring body introduced).
7. The same shapes through a user `macro_rules!`, a wrapper macro, an `assert_eq!` argument, a macro that emits the nested function (and its siblings), local closures that call nested functions, doubly nested functions, nested functions in methods and trait default methods, and macro calls in the members of block-local `impl` blocks.

## Root causes

1. `SourceSyntaxAssembly::next_body_invocation` and `generated_progress` (`expand/source_declarative/body_selection.rs`) demanded only the calls whose innermost owner function is the selected body ("a nested function is independently prepared at entry"). Nothing ever prepared them: `LocalBodyContext::capture` (`frontend/local_body_context.rs`) then proved readiness with `PreparedSourceSyntax::require_closed_function_body` and found the nested function's calls still pending.
2. `EnteredCallGoal::indexed_source_name` compared the call site's index with `retained_plan()`, which for a block item of an enclosing body (`OrdinaryLocalAdmission::is_member`, E-R5-009) is the declaring body's plan, not the call site's.
3. `retained_original_origin` (`frontend/body_type_occurrences.rs`) proves that a Type path of a retained body is original source by locating the body's declaration in the original outline and in the retained unit's anchors. A block-local function is in neither (its identity is minted from its declaring body), so every Type occurrence in a nested body of a macro-expanded enclosing body was `NeedRetainedOccurrence` ("a nested original body's exact original locator is a separate join").
4. `prepare_body_type` (`frontend/body_type_declarations.rs`) looked for the selected declaration's row only in the use-site's own plan, and built the declaration proof on that plan, so a type declared by an enclosing body (selected correctly by the lexical Type prefix, E-R5-009) stopped at `DeclarationOccurrence` and its field types could not be read from the use-site plan.

## Why not a second retained generation per nested function

A block-local function has no retained tree of its own. Its `DefKey` is minted from the declaring body (`syntax/body_items.rs`: parent definition + block scope + name + duplicate ordinal), its `BodyHandle` and `BodyIndex` are read from the declaring body's retained text, and its declaration rows (`DefinitionSource/Header/Body`, `DeclarationContext`, `LocalDeclarationOwner`) are immutable once published. Expanding its calls "at entry" would produce a different retained text under those published rows (a different `body_hash`, different coordinates for the declaring body's own already running frames). The nested calls are therefore attached in the same transaction as the enclosing module-level body's own, in the one retained generation that body already has. This is not a new eager scan: the enclosing body's retained admission already attaches every macro-bearing module-level body at standalone entry (`retained_entry::macro_bearing_bodies`, `admit_retained_body`), and every nested call's output was already issued by the sealed discovery (an unresolved or failing macro in a nested body already stops the run at catalog completion). Only structural attachment is added; nothing is lowered or executed for an uncalled nested function.

## Shared entry points extended (no second route)

- **Source syntax**: `first_call_within(body, owners)` replaces `first_owned_call(body, ..)`. The coordinator loops that already drive module-level bodies (`CompletedSourceSyntax::prepare` for `main` and every macro-bearing body, `prepare_generated` for macro-generated functions) now demand every pending call lying inside the selected body (nested function items, closures, block-level impl/trait members and macro-generated nested items included) in tree order and attach each issued reply through `attach_receipt` unchanged. `finish_for_body` / `finish_for_generated_body` mint the scope only when none remains. A call with no declaration producer (cfg-disabled code) cannot be expanded and keeps blocking only the body that owns it directly, as before (`retained_selected_body_tests::selected_function_executes_while_unowned_cold_calls_remain_pending`). Calls outside the body stay pending.
- **Readiness**: `require_closed_function_body` is unchanged and still fails while a call owned by the entered function remains pending; module-level preparation just no longer leaves the nested functions' calls pending.
- **Call lowering**: `EnteredCallGoal` keeps the call site's plan (`site`) when the admission is detached; `retained_plan()` returns it, so the index, source and structure identities are all the call site's. The admission, guard, signature and body locator stay those of the declaring body (`publish_ordinary_local_function` already skipped only the site-equality checks for `is_member`).
- **Type occurrences**: `retained_original_origin` walks `LocalDeclarationOwner` from the nested body to the outermost original definition, takes that definition's anchor and requires the nested body to lie inside the anchor's body range and the original path to sit inside that definition; the path/token equality and original-hygiene checks are unchanged. Tokens written by an expansion take the existing `Generated` branch (same evidence as for any generated body path).
- **Type declarations**: `prepare_body_type` finds the row in the declaring body's plan (`LocalDeclarationOwner` + `SourceLocalPlan`, both traced as dependencies) when the use-site plan has none, and the `BodyTypeDeclaration` proof is built on that declaring plan so field and schema reads use it. Identity, parse, scope, header and hygiene comparisons are unchanged.

## Removed / superseded

No alternate route is added. Superseded: the innermost-owner filter of the assembly's body scan, the "nested function is independently prepared at entry" comment (it never was), the nested-body `NeedRetainedOccurrence` and `DeclarationOccurrence` outcomes. The adapter's `call_owner_body`/`BodyOwners` remain for producer-less calls and their own tests.

## Cold-path and hot-path cost

Cold: one binary search plus the calls inside the body per attached call (the previous scan had the same shape); one attach per pending call of each nested body, once per module-level body per environment, inside the retained admission that already exists. The Type-occurrence join adds one `LocalDeclarationOwner` input read per nesting level to the Type plan of a nested body (memoized by that plan); the declaration lookup adds one input read and one memoized plan fetch per enclosing-body type, both inside memoized Type queries. Hot: unchanged; the call goal holds one more `Arc` only for detached calls. No namespace census, no source reparse, no deep copy.

## Acceptance scope and known gaps

Tests: `cli/nested_body_tests.rs` (handwritten, user macro, wrapper, macro-emitted; siblings, recursion, closures, doubly nested, methods and trait defaults, local impl members with `write!`/`println!`, Type occurrences, enclosing block types, hygiene, cold nested functions; four editions; rustc outputs); `expand/source_declarative/retained_child_readiness_tests.rs` (a residual call in an entered function still blocks the readiness proof; preparing the enclosing body now demands the nested calls; the residual state is now produced by preparing a sibling body). Unchanged upstream fixtures run (CLI `run`, imported originals under `fixtures/upstream/rustc-checkout/tests/ui`, binary of this tree against the 17:07 binary `lrr-f17`): `fn/expr-fn.rs`, `box/unit/unique-kinds.rs`, `binding/mut-in-ident-patterns.rs` (all three stopped at "local function still has pending expansion calls", now complete) and `array-slice-vec/copy-out-of-array-1.rs` (nested record constructor, now complete). `expr/block-generic.rs` and `expr/if-generic.rs` also complete now (the old binary stopped at `TYPE-SCHEMA: entered source original source owner absent`; their attribution to this change is not isolated). Completed outcomes are runtime-contract runs, not full-fixture passes.

Known gaps (minimal witnesses, rustc accepts all):

1. Qualified paths in the signatures of block-local functions or impl members (`fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result`) stay `NeedOwnerContext` (E-R5-009 gap 3; the `#[ignore]`d `local_impl_tests` case keeps that spelling, the same shapes with module-level `use` run).
2. Method turbofish in a nested body: `fn main() { fn f() -> i32 { "12".parse::<i32>().unwrap() } println!("{}", f()); }` stops at `explicit type needs further source-view integration` (`engine/run.rs`, the legacy explicit-syntax path resolves through the caller's module signature names). The same call in a module-level function runs.
3. A macro-generated module-level function that declares a block-local item: `macro_rules! mk { () => { fn outer() -> i32 { fn inner() -> i32 { 1 } inner() } } } mk!(); fn main() { outer(); }` stops at `LRR-E-BODY-ENVIRONMENT: owning source environment is not published` (the reached-body preparation finds no module source for a generated function; independent of macro calls in the nested body).
4. Block-level `macro_rules!` definitions (`fn main() { macro_rules! m { () => {} } m!(); }`) and the `?` operator are unrelated pre-existing gaps.
