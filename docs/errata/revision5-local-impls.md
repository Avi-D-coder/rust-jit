# E-R5-009 — Block-local `impl` and `trait` declarations

October 17, 2026. Implementation record (not a spec contradiction) under the simple-interpreter scope (E-R5-006 looser than rustc, no resource accounting; E-R5-005 one pipeline). Extends the block-local item work (`cli/local_item_tests.rs`, lexical Value goal in `frontend/source_value_goals.rs`) to `impl` blocks and `trait` declarations written inside function bodies.

## Violated invariant and minimal witnesses

Invariant: an item written in a body behaves like the same item written at module level once its owning body is entered. Witnesses (rustc 1.99.0, all editions):

1. `fn main() { struct S(i32); impl S { fn get(&self) -> i32 { self.0 } fn new(v: i32) -> S { S(v) } } println!("{} {}", S(4).get(), S::new(9).get()); }` prints `4 9` (today: `no method get`).
2. A block-local trait with a required and a provided method, implemented for a block-local struct.
3. A block-local impl of a module trait or a std trait (`Display`, `Default`, `Drop`, `Iterator`, `Add`) for a block-local type; a block-local `impl Foo { fn extra }` on a module type.
4. The same shapes emitted by a user `macro_rules!` and through a wrapper macro.
5. `mod m { pub fn g() {} }` inside a body (`modules/mod-inside-fn`).

## Owner decision (lead)

rustc makes impls inside bodies globally visible. This interpreter keeps preparation lazy, so a block-local impl/trait is published into the member index when its owning body's environment is published (the function is first entered or prepared) and applies to every later method/associated-function selection, including from other functions. Accepted gap: a call that runs before the owning body is first entered (a method of a type whose local impl lives in a function not yet entered) does not see the impl. No eager scan of all bodies.

## Shared entry points extended (no second route)

- **Source facts**: `EnteredMacroFacts.members` (`syntax/entered_macros.rs`, `collect_container_members`): the associated items of every block-level `impl`/`trait` row, built by the one `BodyItemBudget::collect` (`syntax/body_items.rs`, `BodyItemContext.member_owner`). A member's `ItemOutline` follows the module-level convention (`scope.owner == def_key.enclosing_impl ==` the impl identity, or the trait definition; `header.context` the container header). Members are declarations but not lexical names: name-binding consumers (`LocalTypeNames` own rows, item candidates, namespace reads) iterate `items`; declaration consumers (publication, signature/return/parameter goals, local admission, local body capture, nested-body lookup) iterate `EnteredMacroFacts::declarations()` (items then members).
- **Publication**: `Database::prepare_source_local_plan` and `prepare_reached_body_plan` (`db/body_environment_inputs.rs`) already publish every body item through `publish_local_declaration`; they now publish member rows through the same call (a member also publishes its `DefinitionBody` locator, because it is selected by the member index rather than by a lexical call in its owning body) and then call `publish_local_containers`. Item identity includes the owning body (the impl identity is `hash(body-item-scope(parent body, block scope), impl header)`), so two bodies may each declare `struct S` and `impl S`.
- **Impl headers**: `DeclarationFieldTypes::prepare` (`frontend/declaration_field_types.rs`) retains the self-type and trait-path leading-name occurrences of every block-level impl as header Type occurrences. `PreparedSourceLocalPlan::local_containers` (`frontend/local_containers.rs`) enters them through the same lexical Type prefix a local `fn` parameter uses (`lookup_prepared_field_type_prefix`, `select_type_prefix`), so an impl may name a block-local type, an imported type, a module type or a trait; a name no block item/import/generic binds goes to the module graph (`lookup_source_path`) with the whole path.
- **Member index**: `MemberIndex` (`frontend/member_index.rs`) stays immutable per layer. `MemberIndex::publish_local` appends one layer (`next: OnceLock<Arc<MemberIndex>>`) with the body's resolved `LocalContainer`s to the world index; every holder of the world `Arc` (the run machine, the constraint services) sees it without a refresh, nothing of the world is copied or rebuilt, and a body entered twice publishes once (`local_published`). All 35 field reads of the accessors go through `layers()`/`builtin_impls`/`trait_defaults_of`/`lang_item`, so lookups read the world, then the local layers in publication order.
- **Callables**: `member_callee` (`engine/run_trait_calls.rs`) is the single choke point for methods, trait-path calls and operators. `CallResolver::select` (`frontend/callables.rs`) gains the local-member branch next to the generated one: `ordinary_local::admit_container_member` builds the same `SourceCallable` + `OrdinaryLocalAdmission` a block-level `fn` yields (signature fact, input guard, body locator), bound to the member row of the owning body's plan. `OrdinaryLocalAdmission.member` marks an admission that is not tied to a call in the declaring body (members, and block items of an enclosing body named from a nested one); `ReachedLocalBody` (`engine/run_source_preparation.rs`), `publish_ordinary_local_function` and the typed call goal skip only the site-equality checks for it.
- **`Root::function(..)` of a block-bound type**: `RunMachine::select_lexical_associated_call` (`engine/run_nominal.rs`) selects the associated function through `CallResolver::associated_of` for a root the entered Value goal bound lexically.
- **`Self` and receivers of members**: `PreparedSourceLocalPlan::local_self_term`/`local_receiver_term` (a nominal or builtin impl self type read from the member index; a trait member's implicit `Self` parameter), used by the declared parameter goal for receivers and by the header Type prefix for a `Self` leaf.
- **Enclosing block items**: a nested body (a `fn`, or a member) sees the block items of its parents: `LocalTypeNames::prepare` captures the parents' declaration occurrences, the Value goal accepts a declaration owned by an enclosing body (`source_value_goals.rs::declaration`), the dispatcher reads its kind from that body (`run_value_items.rs`), and field projections in a local frame use the frame's published environment (`source_body_context::frame_context`) instead of a module capture. These repair `fn main() { struct S(i32); fn mk(v: i32) -> S { S(v) } .. }`, which failed before for plain nested `fn`s too.

## Removed / superseded

No alternate route is added. Superseded: the opaque treatment of `impl`/`trait` rows in a body (their members were never collected), the `LRR-E-NAME-MISSING` outcome for methods of block-local types, and the module capture of a local frame's body for field projections.

## Cold-path and hot-path cost

Cold, once per body environment publication that has an impl/trait row: one member collection per container (bounded by the container's syntax), one header lookup per impl, one appended layer. Hot: unchanged method probing (`by_nominal` lookup) plus, when the program published any local layer, one extra map lookup per layer (zero extra when none). No per-call source preparation: the callable and its admission are memoized per run in `member_callees`. No whole-world scan or copy.

## Acceptance scope and known gaps

Tests: `cli/local_impl_tests.rs` (handwritten, user macro and wrapper macro in editions 2015-2024; rustc outputs): inherent impl methods and associated functions, local trait with a provided method and a local impl, `impl Iterator`/`impl Add` for a local type, impl on a module type, two bodies declaring the same names. Targeted suites run: `local_item_tests` (14), `ordinary_local*`, `declaration_field*`, `entered_call*`, `body_environment*`, `format_trait_facade*` (one baseline failure, `ordinary_local_publication_checks_actual_owner_header_and_parent_before_mutation`). Explicit gaps:

1. A call that runs before the owning body is first entered does not see the impl (accepted).
2. A member body (or any nested `fn` body) that contains a macro call (`write!`, `println!`) stops with "local function still has pending expansion calls" (`LocalBodyContext::capture` readiness): the nested body's own macro calls are not yet prepared. This blocks local `impl Display`/`Drop` bodies that print (`#[ignore]`d test `block_local_display_default_and_drop_impls_with_macro_bodies`). It is the nested-body macro expansion work of the macro-expansion owner. **Resolved by E-R5-010** ([revision5-nested-body-expansion.md](revision5-nested-body-expansion.md)): nested bodies are demanded and attached with their enclosing body; only the qualified-path signature gap (3) still keeps the `std::fmt::Formatter` spelling of that test ignored.
3. Parameter/return types written as qualified paths (`f: &mut std::fmt::Formatter`) in local declarations stay `NeedOwnerContext` (header shapes capture single names only).
4. Generic local impls (`impl<T> Tr for W<T>`, blanket impls) are skipped at publication (their methods are then reported missing); local `mod` items (`modules/mod-inside-fn`, `#[ignore]`d test); macro calls inside a local container; `#[derive]` on a block-local struct (existing "blocked macro" refusal); a sibling local `fn` calling another local `fn` (`fn a() { b() }`) still stops at "entered call lowering source/body/site differs" (pre-existing; the declaration is now found, the typed call lowering still assumes the site's own body). (E-R5-010 repairs the sibling-call stop.)
5. The drop inventory (`store.install_drop_inventory`) is built once at the first poll: a local `impl Drop` published by a body entered later in the run is not yet in it. A local impl in the entry body publishes before the first poll.
6. Memoized constraint results computed before another body publishes its impls are not invalidated (same accepted gap).
7. Duplicate identical impl headers in one block share an identity.
