# M013 physical child declarative requests

M013 remains in progress. A staged, adopted generated file module can now prepare
an exact item-position declarative expansion request. Preparation re-observes the
module source and compile environment and checks the staged projection identity.
It does not execute a macro, read the filesystem, publish derived database rows,
complete the child producer or release the module frontier.

The existing source macro index resolves the physical child's local textual scope
at its real invocation offset. An unresolved preceding producer suspends lookup;
an annotated call suspends on its attribute input. A locally absent unqualified
name resolves through the retained generated module parent at the declaration's
actual cutoff, including generated ancestors and the original captured parent.
Qualified paths use the existing source/import macro routes and retain their
pending outcome. Local definitions shadow inherited definitions.

Requests own the exact physical invocation token group and its source spans.
Their expansion key includes invocation, input token digest, compile environment,
parent context, definition and call editions, grammar and engine version. The body
comes from the selected child/original source definition or an actual retained
GeneratedItems owner. Generated definition editions are checked. Expansion remains
an explicit separate call to the pinned declarative adapter. Preparing or executing
this request alone does not admit the output into discovery.

Four controls exercise local shadowing, actual identifier/literal arguments, lazy
cold bodies, real generated-parent cutoff, suspension on an earlier producer,
unknown invocation refusal, original-parent body ownership across input replacement,
and annotated producer suspension. These are component controls, not an LRR child
runtime/native comparison or a complete MX027/MX028 acceptance claim.

Worklist-driven child requests and exact output admission, complete namespace import
integration, derived input publication/cache registration, recursive file modules,
included-file physical layout, macro-use exports, final completion proof/frontier
release and actual LRR child execution remain required. Historical positive module
native/LRR evidence remains pending. JIT, release and Linux acceptance remain
unfulfilled. macOS ARM64 with Rust 1.99.0 is the primary validation platform.
